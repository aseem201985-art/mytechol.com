أداء الويب 2025: خطة Core Web Vitals من 4 ثوانٍ إلى ما دون ثانية

INP حلّ محلّ FID، وLCP يتطلب استراتيجية تحميل مختلفة. دليل عملي بالأرقام: ترتيب الأولويات، الحلول الفعلية، وطريقة قياس لا تكذب عليك.

مفريق MyTechol
· 2025-11-20 · 13 دقيقة قراءة · متوسط
CWV

سرعة الموقع ليست رفاهية. في تجارب A/B متكررة عبر مواقع التجارة الإلكترونية، كل 100ms تحسين في LCP ارتبطت بزيادة 0.6–1.2% في معدل التحويل. المشكلة أن معظم الفرق تُحسّن ما تراه في أدوات المطوّر، لا ما يختبره المستخدم.

المقاييس الثلاثة التي تحكم فعلاً

المقياسيقيسجيديحتاج تحسيناً
LCPزمن ظهور أكبر عنصر مرئي≤ 2.5s> 4.0s
INPاستجابة الموقع لكل تفاعل≤ 200ms> 500ms
CLSقفزات التصميم أثناء التحميل≤ 0.1> 0.25
INP حلّ محلّ FID، والفرق جوهري: FID كان يقيس تأخير أول تفاعل فقط، بينما INP يقيس أسوأ تفاعل في الجلسة كلها — بما فيها النقرات أثناء معالجة مهام ثقيلة. لذلك مواقع كثيرة «ناجحة» في FID فشلت في INP.

LCP: لا يوجد حل واحد

أول خطوة: اعرف ما هو عنصر LCP. في 70% من الحالات يكون صورة hero أو h1. لكل حالة علاج مختلف.

{{
index.html
<!-- الصورة الأولى: الأولوية القصوى، بلا كسل -->
<link rel="preload" as="image" href="/hero.avif"
      imagesrcset="/hero-640.avif 640w, /hero-1280.avif 1280w" imagesizes="100vw">

<img src="/hero.avif" width="1280" height="720"
     fetchpriority="high" decoding="async" alt="...">
}}
  • لا تستخدم lazy-loading على صورة LCP — أشهر خطأ وأكثره تكلفة.
  • حدّد الأبعاد دائماً (width/height) لمنع CLS.
  • AVIF ثم WebP — التوفير النموذجي 40–60% مقابل JPEG.
  • لا تُحمّل الخطوط قبل الصورة: font-display: swap وpreconnect فقط.

INP: معركة الخيط الرئيسي

سبب INP السيئ في 90% من الحالات هو مهام طويلة على الخيط الرئيسي: معالجة JavaScript ثقيلة، أو hydration لتطبيق كبير، أو أحداث scroll بلا throttle.

{{
interaction.js
// ✗ خطأ شائع: عمل ثقيل داخل معالج الحدث
button.addEventListener("click", () => {{
  const result = heavyCompute(items);   // 300ms تجميد
  render(result);
}});

// ✓ الحل: أعطِ المتصفح فرصة للرسم أولاً
button.addEventListener("click", async () => {{
  button.classList.add("loading");      // استجابة فورية للمستخدم
  await new Promise(r => setTimeout(r, 0));
  const result = await scheduler.postTask(
    () => heavyCompute(items), {{ priority: "background" }}
  );
  render(result);
}});
}}
قِس دائماً على جهاز متوسط الحال، لا على جهازك. خنق المعالج 4× في أدوات المطوّر يقارب تجربة هاتف من الفئة المتوسطة — وهذا ما يستخدمه معظم زوّارك.

CLS: القفزات التي تُغضب المستخدم

أسباب CLS مرتّبة حسب شيوعها:

  1. صور بلا أبعاد محددة → المتصفح يحجز مساحة صفرية ثم يقفز.
  2. إعلانات أو Embeds تُدرج بعد التحميل بلا حاوية محجوزة.
  3. خطوط تُبدّل بعد التحميل بحجم مختلف بشكل جذري.
  4. إشعارات Cookie تدفع المحتوى من الأعلى.
{{
layout.css
/* احجز المساحة دائماً — aspect-ratio أرخص من أي حل JS */
.media {{ aspect-ratio: 16 / 9; background: var(--surface-2); }}
.media img {{ width: 100%; height: 100%; object-fit: cover; }}

/* الخطوط: قلّل الفرق بين الخط الاحتياطي والخط النهائي */
@font-face {{
  font-family: "Cairo";
  src: url("/fonts/cairo.woff2") format("woff2");
  font-display: swap;
  size-adjust: 103%;      /* يعوّض فرق المقاييس */
}}
}}

ميزانية الأداء: العقد الذي يمنع التراجع

بلا ميزانية مكتوبة، سيعود موقعك للتباطؤ تدريجياً. اكتبها في المستودع وألزم CI بها:

{{
budget.json
{{
  "budgets": [
    {{ "resourceType": "script", "budget": 170 }},
    {{ "resourceType": "stylesheet", "budget": 60 }},
    {{ "resourceType": "image", "budget": 400 }},
    {{ "resourceType": "font", "budget": 90 }},
    {{ "resourceType": "total", "budget": 720 }}
  ]
}}
}}

كيف تقيس بشكل صحيح

البيانات الميدانية (RUM) هي الحقيقة. القياس المخبري مؤشر فقط.

{{
rum.js
new PerformanceObserver((list) => {{
  for (const entry of list.getEntries()) {{
    navigator.sendBeacon("/vitals", JSON.stringify({{
      name: entry.name, value: entry.value,
      rating: entry.rating, id: entry.id
    }}));
  }}
}}).observe({{ type: "largest-contentful-paint", buffered: true }});
}}
الخطوة التالية: افتح PageSpeed Insights على موقعك، وحدّد عنصر LCP بالضبط قبل أي تعديل. ثم عالج أكبر مقياس متأخر فقط — لا تعالج الثلاثة معاً.
