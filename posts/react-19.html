React 19: ما الذي يتغير فعلياً في طريقة كتابة الكومبوننتس؟

نظرة معمّقة على Actions و useOptimistic و Server Components، ومتى تستخدم كل واحدة منها في مشروع حقيقي.

ععاصم محمد
· 2025-02-11 · 11 دقيقة قراءة · متقدم

React 19 ليست تحديثاً تجميلياً. أكبر تغيير فيها ليس ميزة جديدة، بل تغيير في نموذج التفكير: من «أدر الحالة يدوياً وارسم الشاشات» إلى «أرسل الفعل (Action) ودع React يدير الانتظار والخطأ والحالة المتفائلة».

Actions: النماذج أخيراً

قبل React 19، أي إرسال نموذج كان يكلّفك ثلاثة متغيرات على الأقل:

// النمط القديم
const [loading, setLoading] = useState(false);
const [error, setError] = useState(null);

async function handleSubmit(e) {
  e.preventDefault();
  setLoading(true);
  setError(null);
  try {
    await saveUser(new FormData(e.target));
  } catch (err) {
    setError(err.message);
  } finally {
    setLoading(false);
  }
}

في React 19 يمكنك تمرير دالة غير متزامنة مباشرة إلى action:

// React 19
async function saveUser(formData) {
  const name = formData.get("name");
  await api.updateUser({ name });
}

export default function ProfileForm() {
  return (
    <form action={saveUser}>
      <input name="name" required />
      <SubmitButton />
    </form>
  );
}

React يتولّى: منع الإرسال المزدوج، إعادة التصفير بعد النجاح، وحالة الانتظار. هذا وفر الكثير من الكود المكرر في كل مشروع.

useOptimistic

المستخدم لا يحب الانتظار. useOptimistic يحدّث الواجهة فوراً قبل أن يعود الخادم، ثم يصحّحها لو فشل الطلب:

"use client";
import { useOptimistic, useRef } from "react";

export function MessageList({ messages, sendMessage }) {
  const formRef = useRef(null);

  const [optimisticMessages, addOptimistic] = useOptimistic(
    messages,
    (state, newText) => [...state, { id: "temp", text: newText, sending: true }]
  );

  async function formAction(formData) {
    const text = formData.get("text");
    addOptimistic(text);        // تظهر فوراً
    formRef.current.reset();
    await sendMessage(text);    // إن فشلت، تُصحّح القائمة تلقائياً
  }

  return (
    <>
      {optimisticMessages.map(m => (
        <div key={m.id} style={{ opacity: m.sending ? 0.5 : 1 }}>{m.text}</div>
      ))}
      <form ref={formRef} action={formAction}>
        <input name="text" required />
        <button>إرسال</button>
      </form>
    </>
  );
}
قاعدة مهمة: القيمة المتفائلة مؤقتة بطبيعتها. لا تستخدمها لقرارات حرجة (مثل الرصيد المالي) — استخدمها للتفاعلات التي يعرف المستخدم نتيجتها مسبقاً.

useFormStatus و useActionState

useFormStatus يجب أن يُستخدم داخل مكوّن فرعي للنموذج، وهذا مصدر خطأ شائع:

import { useFormStatus } from "react-dom";

function SubmitButton() {
  const { pending } = useFormStatus();   // يجب أن يكون داخل مكوّن فرعي
  return <button disabled={pending}>{pending ? "جارٍ الحفظ…" : "حفظ"}</button>;
}

وuseActionState يجمع الحالة والخطأ والنتيجة في خطاف واحد:

import { useActionState } from "react";

async function loginAction(prevState, formData) {
  const res = await api.login(formData.get("email"), formData.get("password"));
  if (!res.ok) return { error: "بيانات الدخول غير صحيحة" };
  return { success: true };
}

export function LoginForm() {
  const [state, formAction, isPending] = useActionState(loginAction, {});

  return (
    <form action={formAction}>
      <input name="email" type="email" required />
      <input name="password" type="password" required />
      {state.error && <p style={{ color: "tomato" }}>{state.error}</p>}
      <button disabled={isPending}>دخول</button>
    </form>
  );
}

Server Components

الفرق الجوهري ليس تقنياً فقط، بل في حجم ما يُرسل إلى المتصفح. في السابق كان استعلام قاعدة البيانات يتم عبر API ثم يُرسل JSON؛ الآن يُنفَّذ على الخادم ويُرسل واجهة جاهزة — بلا مكتبة ثقيلة في الحزمة.

// app/users/page.tsx — مكوّن خادم (افتراضياً)
import { db } from "@/lib/db";

export default async function UsersPage() {
  const users = await db.user.findMany({ take: 20 });

  return (
    <ul>
      {users.map(u => <li key={u.id}>{u.name} — {u.email}</li>)}
    </ul>
  );
}

لاحظ: مكوّن async، بلا useEffect، بلا حالة تحميل، بلا طلب شبكة من المتصفح. قاعدة صريحة: لا يمكن لمكوّن خادم أن يستخدم useState أو useEffect أو أحداث DOM. إن احتجت تفاعلاً، أضف "use client" في مكوّن صغير معزول.

خطة الترحيل

  1. ابدأ من النماذج: استبدل onSubmit + useState بـ action. أقل مخاطرة وأكبر مكسب.
  2. انقل الطبقة الثابتة إلى Server Components قبل الطبقة التفاعلية.
  3. لا تنقل كل شيء: الصفحات التفاعلية بالكامل تبقى كما هي.
  4. اختبر التحديث المتفائل بحالة فشل متعمّد — هنا تظهر الأخطاء.
  5. راقب حجم الحزمة قبل/بعد؛ هذا هو المؤشر الحقيقي للنجاح.

متى لا تستخدمها؟

  • تطبيق لوحة تحكم داخلي بالكامل تفاعلي — Server Components لن تضيف كثيراً.
  • مشروع قديم كبير (Legacy) بلا فريق مستعد للصيانة.
  • حين لا تحتاج SEO ولا تحسين الحزمة الأولى.
الخطوة التالية: افتح أي نموذج في مشروعك، واحذف useState للتحميل والخطأ، واستبدلهما بـ useActionState. ستوفّر ما بين 15 و 30 سطراً في كل نموذج.
