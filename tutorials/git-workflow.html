Git و GitHub من البداية: سير عمل آمن لفريق

لا أوامر محفوظة بلا فهم. سنبني المستودع، ننشئ فروعاً، نحل تعارضاً مقصوداً، ثم نمرّر أول Pull Request كما تفعل في عمل حقيقي.

أفريق MyTechol
· 2025-11-23 · 13 دقيقة قراءة · متوسط
git

Git ليس أداة اختيارية. هو الشيء الذي يمنعك من فقدان يوم كامل من العمل، ويسمح لثلاثة أشخاص بتعديل الملف نفسه دون فوضى. من لا يفهمه يخافه، ومن يفهمه لا يعمل بدونه.

سنمشي بترتيب معيّن: الفكرة أولاً، ثم الأوامر، ثم السير العمل كاملاً.

1. الفكرة قبل الأوامر

تخيّل Git كسلسلة صور لحظية للمشروع. كل صورة تسمى commit وتحتوي على حالة كل الملفات في لحظة معيّنة، مع سبب التغيير. تستطيع العودة لأي صورة في أي وقت.

ثلاث مناطق تفهمها مرة واحدة:

المنطقةمعناهاالأمر
Working Directoryملفاتك كما تراها الآنتحرّر هنا
Staging Areaما اخترته للصورة القادمةgit add
Repositoryالصور المحفوظةgit commit

لماذا الـ staging موجودة أصلاً؟ لأنها تمكّنك من تقسيم عملك: عدّلت 5 ملفات لكنك تريد حفظ إصلاح الخطأ وحده في commit منفصل. هذه النظافة هي الفرق بين سجل تاريخي مفيد وسجل عشوائي.

2. الإعداد الأولي

# مرة واحدة على جهازك
git config --global user.name "اسمك"
git config --global user.email "you@example.com"

# اجعل الفرع الافتراضي main (المعيار الحالي)
git config --global init.defaultBranch main

هذه الإعدادات تُطبَع داخل كل commit، فتصبح قادراً على معرفة من عدّل ماذا.

3. المستودع الأول

mkdir my-project
cd my-project
git init                    # ابدأ مستودعاً جديداً

# ملف .gitignore — أهم ملف في المشروع
echo "node_modules/" >> .gitignore
echo ".env"          >> .gitignore
echo "*.log"         >> .gitignore
حرج: أضف ملف .gitignore قبل أول commit. إذا رفعت ملف .env أو مفتاحاً سرياً مرة واحدة، فسيبقى في تاريخ المشروع للأبد حتى لو حذفته لاحقاً — والحل الوحيد هو إبطال المفتاح من مصدره.

ثم الدورة اليومية:

git status                 # ماذا تغيّر؟
git diff                   # ماذا في التغييرات فعلاً؟
git add index.html         # حدّد ملفاً
git add .                  # أو كل شيء
git commit -m "إضافة الصفحة الرئيسية"

افحص قبل كل commit أمرين: git status لتعرف ما سيدخل، وgit diff لتعرف ماذا تغيّر فعلاً. هذان الأمران وحدهما يمنعان معظم أخطاء الرفع.

4. كيف تكتب commit يفيدك بعد ستة أشهر

❌ git commit -m "update"
❌ git commit -m "fix"
❌ git commit -m "تعديلات"

✅ git commit -m "fix: منع تكرار إرسال النموذج عند النقر المزدوج"
✅ git commit -m "feat: إضافة فلترة المقالات حسب القسم"
✅ git commit -m "refactor: فصل منطق المصادقة عن مكوّن العرض"

اتفاقية شائعة ومفيدة:

feat:      ميزة جديدة
fix:       إصلاح خطأ
refactor:  تحسين بلا تغيير سلوك
docs:      توثيق
style:     تنسيق فقط
test:      اختبارات
chore:     صيانة وأدوات

5. الفروع: تجربة بلا خوف

الفرع نسخة منفصلة تعمل عليها. تعديلك لا يمسّ main حتى تدمجه. هذه هي الطريقة الوحيدة للعمل بأمان.

git branch                       # قائمة الفروع
git switch -c feature/login      # أنشئ فرعاً وانتقل إليه

# اعمل، أضف، ثم حدّث
git add .
git commit -m "feat: صفحة تسجيل الدخول"

git switch main                  # عد إلى الفرع الرئيسي
git merge feature/login          # ادمج

لتحديث فرعك بما استجد على main قبل الدمج (الطريقة الآمنة):

git switch main
git pull origin main
git switch feature/login
git rebase main            # أعِد تطبيق تعديلاتك فوق آخر نسخة

6. حل التعارض — بلا رعب

التعارض ليس خطأ. هو مجرد حالة عدّل فيها شخصان السطر نفسه، وGit لا يعرف أيهما تريد.

عند التعارض يضع Git علامات في الملف:

<<<<<<< HEAD
const URL = "https://api.example.com/v1";
=======
const URL = "https://api.example.com/v2";
>>>>>>> feature/login

ما فوق ======= هو نسختك، وما تحته نسخة الفرع الآخر. الحل بثلاث خطوات:

1. احذف علامات <<<<<<< و ======= و >>>>>>>
2. اترك الكود الصحيح فقط (واحدة أو دمج الاثنتين)
3. git add الملف المحلول
4. git commit          ← يُنهي العملية

# تراجعت؟ عد لحالة ما قبل الدمج
git merge --abort

قاعدة عملية: قبل كتابة أي كود جديد في اليوم، نفّذ git pull. هذا يقلل التعارضات أكثر من أي تقنية أخرى.

7. GitHub: العمل عن بُعد

# اربط مستودعك المحلي بمستودع GitHub
git remote add origin https://github.com/USERNAME/REPO.git

# أول رفع
git push -u origin main

# بعد ذلك، لكل تعديل
git add . && git commit -m "feat: ..." && git push

وتوثيق الرفع يُفضَّل بـ SSH بدلاً من كلمة المرور:

ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub     # انسخ الناتج
# الصقه في GitHub → Settings → SSH and GPG keys → New SSH key

8. سير العمل الحقيقي: Pull Request

هكذا يعمل الفريق فعلاً — حتى لو كنت وحدك، اتبع هذه الدورة:

1. git switch -c feature/new-navbar
2. اعمل واختبر
3. git add . && git commit -m "feat: شريط تنقل جديد"
4. git push -u origin feature/new-navbar
5. على GitHub: افتح Pull Request
6. راجع، اطلب تعديلات، أو ادمج
7. git switch main && git pull
8. git branch -d feature/new-navbar    # نظّف

لماذا PR وليس دمجاً مباشراً؟ لأنه يخلق نقطة مراجعة واضحة: ماذا تغيّر، لماذا، وهل يمرر الاختبارات. هو أيضاً سجل مكتوب لقرارات المشروع.

9. أوامر الإنقاذ

ستحتاجها — والذعر ليس حلاً:

# تراجع عن تعديل ملف قبل الإضافة
git restore file.js

# تراجع عن git add
git restore --staged file.js

# عدّل آخر commit (الرسالة أو المحتوى)
git commit --amend

# ألغِ commit مع الحفاظ على التعديلات
git reset --soft HEAD~1

# احفظ عملك مؤقتاً لتنتقل لشيء آخر
git stash
git stash pop

# عرض تاريخ مختصر مرتّب
git log --oneline --graph -15

# من عدّل هذا السطر؟
git blame file.js
قاعدة ذهبية: لا تستخدم git push --force على فرع مشترك. قد تمحو عمل زملائك بصمت. إذا احتجت إجبار الرفع على فرعك الشخصي فقط، استخدم --force-with-lease.
الخطوة التالية: أنشئ مستودعاً وهمياً الآن، أنشئ فرعين وعدّل السطر نفسه في كل واحد، ثم ادمجهما وشاهد التعارض بعينك. حلّ تعارضاً واحداً بنفسك يعادل حفظ عشرين أمراً.
