PostgreSQL: 12 إعداداً تفرّق بين قاعدة بطيئة وأخرى فائقة

القيم الافتراضية تكفي للتجربة لا للإنتاج. دليل عملي لضبط الذاكرة والمخططات والاستعلامات، مع طريقة قراءة EXPLAIN ANALYZE كما يفعل المحترفون.

مفريق MyTechol
· 2025-11-22 · 14 دقيقة قراءة · متوسط
PGSQL

تثبيت PostgreSQL الافتراضي مضبوط على جهاز بـ 512MB RAM من سنة 2008. إن لم تغيّر الإعدادات، فأنت تُشغّل قاعدة بيانات مُقيَّدة عمداً.

الذاكرة: الأهم أولاً

القاعدة الإرشادية: shared_buffers = 25% من الذاكرة، وeffective_cache_size = 50–75% (تقدير لما يستطيع نظام التشغيل تخزينه).

{{
postgresql.conf
# postgresql.conf — لخادم 16GB RAM مخصص لقاعدة البيانات

shared_buffers = 4GB              # 25% — كاش داخل PostgreSQL
effective_cache_size = 10GB       # 65% — تقدير كاش نظام التشغيل
work_mem = 32MB                   # لكل عملية فرز/هاش — انتبه للتزامن!
maintenance_work_mem = 1GB        # لـ VACUUM و CREATE INDEX
max_connections = 100             # أبقِه منخفضاً واستخدم pooler
}}
تحذير تكلفة: work_mem تُضرب في عدد العمليات المتزامنة. مع max_connections=100 وwork_mem=256MB يمكن أن تستهلك 25GB دفعة واحدة وتُسقط الخادم. ابدأ صغيراً وزد عند الحاجة الفعلية.

الاختبار العملي

{{
cache.sql
-- هل الـ cache فعّال؟ نسبة القراءة من الذاكرة يجب أن تقارب 99%
SELECT
  sum(blks_hit) * 100.0 / nullif(sum(blks_hit + blks_read), 0) AS cache_hit_pct,
  pg_size_pretty(pg_database_size(current_database())) AS db_size
FROM pg_stat_database;
}}

WAL والكتابة

{{
wal.conf
# توازن بين الأمان والسرعة
wal_level = replica               # مطلوب للنسخ الاحتياطي والقراءة المتماثلة
max_wal_size = 4GB                # تقليل checkpoints المتكررة
min_wal_size = 1GB
checkpoint_completion_target = 0.9

# SSD حديث؟ زد التزامن
effective_io_concurrency = 200
random_page_cost = 1.1            # افتراضي 4.0 للـ HDD — خطأ شائع على SSD
}}

random_page_cost=4.0 على قرص SSD يجعل المخطِّط يتجنّب الفهارس ظناً أنها «مكلفة» — فيختار مسحاً كاملاً للجدول. تغيير هذا الرقم وحده كثيراً ما يقلّل زمن الاستعلام من ثوانٍ إلى أجزاء من الثانية.

الفهارس الصحيحة

{{
indexes.sql
-- 1) فهرس مركّب: ترتيب الأعمدة يهم
--    يساعد: WHERE tenant_id = ? AND created_at > ?
CREATE INDEX CONCURRENTLY idx_orders_tenant_created
  ON orders (tenant_id, created_at DESC);

-- 2) فهرس جزئي: أصغر وأسرع للاستعلامات الشائعة
CREATE INDEX CONCURRENTLY idx_orders_pending
  ON orders (created_at) WHERE status = 'pending';

-- 3) فهرس تغطية: يخدم الاستعلام دون لمس الجدول (Index Only Scan)
CREATE INDEX CONCURRENTLY idx_orders_cover
  ON orders (tenant_id, created_at) INCLUDE (total, status);
}}

{{
dead-indexes.sql
-- اعثر على الفهارس الميّتة (لم تُستخدم قط)
SELECT schemaname, relname, indexrelname, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND indexrelname NOT LIKE '%_pkey'
ORDER BY pg_relation_size(indexrelid) DESC;
}}

قراءة EXPLAIN كما يفعل المحترفون

استخدم EXPLAIN (ANALYZE, BUFFERS) — نسبة الوقت في القاعدة وحدها دون BUFFERS تُخفي أن الاستعلام يقرأ من القرص.

{{
explain.sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT o.id, o.total
FROM orders o
WHERE o.tenant_id = 42 AND o.status = 'pending'
ORDER BY o.created_at DESC
LIMIT 20;

-- ابحث في المخرجات عن:
--   Seq Scan         -> غالباً تحتاج فهرساً
--   Rows Removed by Filter: رقم ضخم -> الفهرس غير انتقائي
--   Buffers: read   -> قراءة من القرص (بطيئة)
--   Buffers: hit    -> من الذاكرة (سريعة)
--   Sort Method: external merge Disk -> work_mem صغير جداً
}}

Vacuum: ما لا يعرفه كثيرون

PostgreSQL لا يحذف الصفوف فعلياً عند DELETE — يعلّمها ميتة. VACUUM يستعيد المساحة. بدون ضبط، تتضخم الجداول وتتباطأ الاستعلامات بمرور الشهور.

{{
bloat.sql
-- راقب الجداول المتضخّمة (تحتاج امتداد pgstattuple)
SELECT relname,
       n_live_tup, n_dead_tup,
       round(n_dead_tup * 100.0 / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 1000
ORDER BY dead_pct DESC;
}} {{
autovacuum.conf
# للجداول كثيفة التحديث
autovacuum_vacuum_scale_factor = 0.02    # بدل 0.2
autovacuum_analyze_scale_factor = 0.01
autovacuum_naptime = 30s
}}

قائمة تحقّق سريعة

  1. اضبط shared_buffers وeffective_cache_size.
  2. غيّر random_page_cost إلى 1.1 على SSD.
  3. شغّل pg_stat_statements وراقب أبطأ 10 استعلامات.
  4. اعثر على الفهارس غير المستخدمة واحذفها.
  5. راقب نسبة الصفوف الميتة أسبوعياً.
  6. خذ نسخة احتياطية واختبر استعادتها — النسخة غير المُختبرة ليست نسخة.
{{
top-queries.sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT calls, round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS avg_ms,
       left(query, 90) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
}}
الخطوة التالية: شغّل آخر استعلام في قائمتك، ثم أول استعلام في قائمة أبطأ الاستعلامات. الفرق بين الرقمين سيحدد أين تبدأ غداً.
